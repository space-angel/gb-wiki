# 프로젝트 현황 진단과 개편 기준

> **2026-09-08 사용자 지정:** 이 문서를 로드맵 개편 기준으로 삼는다. 로드맵 폴더의 나머지 9개 문서(기존 스프린트·장면·담당별 계획·브리프·주간 미팅·Linear 운영 초안)는 폐기했다. 아래의 기존 계획에 대한 평가는 진단 당시의 기록이며, 해당 계획의 일정·담당·운영 규칙을 승계하지 않는다. 이 문서 안의 작업 순서·착수 후보는 새 로드맵을 구성할 때 검토할 제안이다.

**현재는 ADR로 정한 규칙과 작성 중인 기획을, 실제로 플레이할 수 있는 게임으로 연결해야 하는 단계다.**
기존 기획과 구현 자산을 확인하고, 작은 구간의 진행 조건을 합의한 뒤 제작 범위를 잡는 것이 다음 작업이다.

## 1. 이번 진단의 기준

- **사용자 확인(2026-09-08): 플레이 가능한 것은 없다. 나머지 기획은 전부 작업 중이다.** 문서 안의 `확정`, `완료` 표기만으로 기획 완료를 인정하지 않는다.
- ADR 원문 파일은 **15건: Accepted 11건(1~10, 15), Proposed 4건(11~14)**이다. 사용자 설명에서 ADR을 기준으로 삼되, 제안 상태인 ADR까지 확정으로 올려 해석하지 않는다.
- 조사 전 로컬 Markdown **230개**의 파일 구성·분량을 확인했다. 게임가이드 38, 게임시스템 확정본 17, 로드맵 8, raw 167개다. ADR·현황·현재 챕터 기획·운영 계획·관련 회의록을 중심으로 본문을 대조했다. 모든 원문을 문장 단위로 재감사한 결과는 아니다.
- 위키는 최신 외부 작업의 전수 목록이 아니다. 마지막 전체 대조는 **8월 17일**, 9월 7일은 미래축·상담사 부분 대조다. 동기화 기록에는 **미반영 Notion 변경분 32건**이 남아 있다. 아트 이미지·첨부파일·Unity 프로젝트·현재 Notion 원문은 이번 진단에서 직접 검증하지 않았다.[S1]
- 따라서 `위키에서 확인 안 됨`과 `실제로 제작하지 않음`을 구분한다. 특히 **플레이 가능한 빌드 없음 ≠ 재사용할 코드·아트 없음**이다.

## 3. 작업을 연결할 때 막히는 핵심 항목

아래는 결정 후보 목록이다. 결론을 새로 확정한 것이 아니다. 기존 `06-03`의 C-1~4와 연결해 관리하고, 같은 사안을 다른 이름으로 중복 이슈화하지 않는다.

### A. 무엇을 발견하고, 무엇을 선택하면, 어디가 열리는가

- 스토리 진행안: 메인 유품 3종을 원룸에서 동시 발견 → 하나 선택 → 첫 축 이후 나머지 축 진행.
- ADR-11(Proposed): 앞 구역에서 다음 구역의 메인 유품을 얻는 순차 체인.
- 메인 유품의 실제 목록도 스토리와 ADR-13(Proposed)이 다르다.
- **필요한 산출물:** 유품별 `발견 위치 / 조사 조건 / 획득 조건 / 여는 구역 / 다음 축 개방 조건` 표. 발견·조사·보유·선택을 같은 상태로 취급하지 않아야 한다.
- **영향:** 레벨 배치, 콘텐츠 순서, 인벤토리·저장 데이터. 단순 이동·조사 기능 시험까지 모두 막는 것은 아니다.[S3][S4][S8]

### B. O/A/V/R이 구체적으로 무엇을 하면 바뀌는가

- ADR-3 및 `01-05`: O는 **핵심 3개 전부 발견 + 보조 N개**.
- ADR-12(Proposed) 및 `01-04`: O는 **보조 N개 확보(판매분 제외)**.
- 7월 20일 회의록: O를 **메인 A + 보조 N개**로 축소했다는 보고.
- 3축의 기여는 R / A+V / V로 적혀 있으나, 플래그를 축별로 갖는지 챕터 전체가 공유하는지도 비어 있다.
- **필요한 산출물:** `행동 전 상태 → 플레이어 행동 → 행동 후 상태 → 새로 가능한 행동` 표. O 정의를 바꾸려면 ADR-3의 해당 조항 개정 여부까지 명시한다. N만 임시로 넣어서는 이 차이가 해결되지 않는다.[S3][S6][S9]

### C. 단서로 NPC 기억이 열리는 흐름과 시스템 규칙의 관계

- 상담사 대본은 취준 파일 → 센터 정보단서 → 다이어리 → 정장·영수증 → 마지막 방문 회상으로 점진 공개된다.
- ADR-6(Accepted)은 A/V 핵심 진술자 분리와 각 최소 2명을 요구한다. 현재 NPC 배정과 맞춰야 한다.
- ADR-11(Proposed)은 사령 단서가 현실 추리 단계를 여는 트리거를 금지한다. ADR-13(Proposed)은 페어링을 해금 조건에 넣지 않도록 한다. 실제 대본의 단서별 공개 조건과 어디까지 양립하는지 설명이 필요하다.
- **필요한 산출물:** NPC 대사 단계별 `필요한 증거 / 공개 정보 / A·V·R 기여 여부 / 회상 위치` 표. 일반 대화 공개와 이해도 판정을 구분해서, 실제 충돌 범위를 판정한다.
- 단서에 따라 대사가 바뀌는 기술 구현만으로 이 기획 문제가 해소되지는 않는다. 반대로 모든 대화를 A/V 핵심 진술로 간주해서도 안 된다.[S3][S5][S8]

### D. ‘한 조사축 완료’와 ‘챕터의 재해석 완료’의 차이

- 현재 흐름에는 첫 조사축 완료 후 나머지 두 축 개방이 있다. 구체 조건은 후보가 남아 있다.
- 미래축만으로 고인의 전체 내면을 설명하지 않는다는 제한이 대본에 명시되어 있다.
- **필요한 산출물:** 첫 축의 종료 조건, 다른 축 개방 조건, 최종 보드·R 판정의 범위를 구분한 진행표.
- 하나의 축에서 무엇까지 검증하는지 정해야, 첫 실험 성공을 챕터 전체 설계 검증으로 오해하지 않는다.[S4][S5]

### E. 판매·오답·조기 보스 진입 뒤에 무엇이 남는가

- 보조유품 판매와 소멸 루트는 연결되지만, 이미 얻은 이해·진술·회상·구역이 어떻게 되는지 전 상태가 정리되지 않았다.
- 7월 20일 회의록에는 ‘판매 후에도 플래그 유지?’에 ‘아뇨’가 적혀 있다. 이를 실행 가능한 리셋·재판정 규칙으로 정리한 근거가 더 필요하다.
- ADR-14의 상태 보존은 **오답 처리**에 관한 제안이므로, 이것만으로 판매 이후 보존 여부까지 결정할 수 없다.
- **필요한 산출물:** `판매 전후 / 오답 전후 / R 미달 보스 진입 / 패배·복귀`에 대한 상태·결과 표.
- **영향:** 저장·불러오기, 진행 막힘, 상점, 종결. 기본 이동 실험 뒤로 미룰 수 있지만 해당 기능을 구현하기 전에는 필요하다.[S6][S10]

### F. 사령세계의 구체적인 플레이가 아직 없다

- 감정·미술 컨셉과 실제로 걸어 다니며 조사하고 회피하는 레벨은 별도 산출물이다.
- 로컬의 사령세계 상세 설계는 스텁이고, 미래축의 ‘끝나지 않는 면접’도 맵·패턴으로 연결되지 않았다.
- **필요한 산출물:** 한 공간의 이동 경로, 조사 위치, 단서 공개 순서, 회피 행동, 나오는 방법을 담은 러프. 완성 아트보다 먼저 플레이 흐름을 확인한다.[S4][S7]

## 4. 위키 자체에서 정리할 문제

| 발견 | 의미 | 처리 방향 |
|---|---|---|
| ADR-15·`01-05`는 보조 6개인데 `전체_요약`, `01-04`, `06-02`, 시스템 전체 구조에는 보조 10~12 또는 총 13~15가 남아 있음 | 현재 규칙을 찾는 진입점끼리도 값이 다름 | 개정 근거가 명백한 요약부터 동기화. N값·O조건까지 임의로 확정하지 않음 |
| ‘확정본’ 폴더에도 Proposed 문서가 있고, 일부 문서 안에서 확정·잠정이 섞임 | 폴더명·문서 작성 여부가 승인 상태처럼 읽힐 수 있음 | 결정 상태는 ADR별, 콘텐츠 상태는 산출물별로 표시 |
| 상담사 상세본의 원문 상태는 `작성됨`, 옛 로드맵은 장면 3~7 스토리를 `완료`로 표시 | 작성 완료와 제작 투입 가능 여부가 섞임 | 현재는 작성 중인 기획 자산으로 집계. 시험에 사용할 부분의 검토 결과를 따로 기록 |
| 9월 7일 부분 동기화 이후에도 32건 미반영 기록 | 로컬 빈칸이 이미 외부에서 채워졌을 가능성 | 새 작업 발행 전에 기존 산출물 링크부터 대조 |
| 기존 감사의 ‘갈림 4건·위반 14건’은 과거 집계 | 이를 현재의 전체 미완료 작업 수로 사용할 수 없음 | 실제 사용할 문서를 중심으로 항목을 갱신 |

현재 `06-03`에 추가하거나 확장할 후보는 **O 조건의 세 버전, 단서별 대화 해금과 ADR-11/13 관계, 판매 이후 상태 규칙**이다. 이번 진단에서는 쟁점을 식별했으며 어느 설계를 채택할지는 정하지 않았다.

## 5. 폐기한 계획의 진단 기록과 새 개편에 반영할 점

**살릴 요소:** 같은 플레이 결과를 목표로 협업하기, 산출물 단위로 쪼개기, 담당자와 완료 기준을 명시하기, 동시에 벌이는 작업을 줄이기.

**다시 설계할 요소:**

1. **날짜와 완료 가정.** 기존 날짜는 현재 진행 증거와 팀별 가용시간으로 재산정한다. 2027년 6월 데모는 문서에 있는 목표이며, 이번 대화에서 재확인된 약속은 아니다.
2. **‘결정 대기 없음’의 범위.** 이동·텍스트 카드 실험은 가능하지만, 완성 게임에 사용할 대화·진행 규칙까지 확정된 것은 아니다.
3. **검증의 깊이.** 물건 2개를 조사하면 대사가 바뀌는 실험은 유용한 첫 단계다. 다만 가설·교차검증·재해석·종결까지 검증한 것으로 집계할 수 없다.
4. **완료의 기준.** 기획·아트는 ‘공유했다’로 끝내면 다음 사람이 사용하기 어려운 상태가 남는다. 산출물의 수신자가 사용할 수 있는지 확인하고, 게임 통합은 별도 작업으로 연결한다.
5. **PM 업무 집중.** 옛 계획은 PM에게 상태 갱신·문서 동기화·대사 변환·통합·결정 대행을 모은다. 개발까지 겸하면 병목이 될 수 있다는 진단이다. 실제 역할은 현재 팀 상황에 맞춰 다시 정해야 한다.
6. **정본 관리.** 기존 계획은 모두 폐기했고, 이 문서가 새 로드맵의 출발점이다. 이후 새 일정·담당표가 생기면 개편 기준과의 관계 및 적용 시점을 명시한다.
7. **운영 방식도 새로 결정.** 함께 폐기한 9월 8일 Linear 운영 초안에는 각자 직접 갱신하고 프로젝트·사이클·부모 이슈를 사용하지 않는 안이 있었다. 이 안도 승계하지 않는다. 당시 초안의 실패 원인 분석과 외부 상태 수치는 이번 위키 진단에서 별도로 검증하지 않았다. 사이클을 사용할지 여부와 관계없이, 공동 목표·인계 기준·진행 증거가 필요하다.[S12]

근거: [S11]. 위 내용은 운영 개선 제안이며, 팀원의 실제 작업 태도나 지연 원인을 단정한 것은 아니다.

## 6. 개편 후 작업의 큰 순서 — 날짜 없는 제안

| 단계 | 확인할 결과 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1. 현재 자산·규칙 기준 정리 | 사용할 문서·코드·에셋 목록, Accepted/Proposed 경계, 첫 실험 후보 | 재사용할 것과 새로 만들 것을 구분할 수 있음 |
| 2. 첫 조사 구간 설계와 상호작용 시험 | 짧은 진행표 + 이동·조사·텍스트·대화 시험 | 누가 봐도 같은 순서·조건으로 실행되고 첫 질문을 검증할 수 있음 |
| 3. 한 구간의 추리·재해석 시험 | 증거·진술·가설·결과를 연결한 플레이 | 왜 해석이 바뀌었는지, 막히는 분기가 무엇인지 확인 가능 |
| 4. 현실↔사령·전투·처분 연결 | 공간 왕복, 회피, 판매, 복귀·종결 결과 | 이해를 진행하거나 멈춰도 의도한 경로가 성립 |
| 5. 챕터1 콘텐츠 확장 | 남은 축·NPC·맵·아트·UI·사운드·저장 연결 | 전체 흐름이 같은 빌드에서 이어지고 반복 플레이 가능 |
| 6. 데모 마감 작업 | 온보딩, 가독성, 진행 오류, 성능, 배포 빌드 점검 | 합의한 데모 범위와 품질 기준 충족 |

첫 조사 구간의 후보는 기존 이유미 구간과 상세 자료가 있는 미래축 일부다. 전자는 공간 범위가 작고, 후자는 기존 대본이 풍부하다. **현재 재사용 자산과 무엇을 먼저 검증할지에 따라 선택**한다. 미래축 전체를 먼저 만든다거나, 옛 8개 장면을 그대로 일정화한다는 뜻은 아니다.

## 7. Linear에 옮기기 전 준비할 착수 작업 후보

아래 표는 발행·배정 전 초안이다. 첫 사이클에 전부 넣지 않는다. 역할 표기는 기존 문서의 역할을 참고한 것이며 현재 담당·투입시간은 미확인이다.

| 작업 후보 | 중심 역할 | 끝났다는 증거 | 선행·선택 조건 |
|---|---|---|---|
| 현재 기획·코드·아트 자산 목록 확인 | PM 취합, 각 파트 확인 | 원본 링크·최종 확인일·현재 사용 가능 여부 목록. 코드는 실행 결과 포함 | 바로 시작 가능 |
| 첫 실험의 질문과 범위 정하기 | 기획, 스토리·개발 검토 | 시험할 플레이 결과 1개, 포함 기능·콘텐츠, 성공 판단 방법 | 자산 목록으로 범위 조정 |
| 첫 구간의 행동·정보·상태 진행표 작성 | 기획 중심, 스토리·개발 검토 | 각 행동의 전후 상태·단서·대사·종료 조건. 미결 지점은 별도 표시 | 첫 구간 선정. 전체 설계 충돌은 범위에 필요한 것부터 처리 |
| 선택한 구간의 대사·조사 텍스트 묶기 | 스토리 중심 | 실제 사용할 텍스트와 공개 조건, 출처, 검토 결과 | 진행표와 맞춰 작업. 기존 대본 우선 활용 |
| 첫 공간의 동선 러프와 가독성 확인 | 레벨 기획 중심, 아트·개발 검토 | 이동·조사·대화 위치 표시, 충돌·크기 기준을 시험 화면에서 확인 | 범위 선정. 임시 도형 활용 가능 |
| 기존 프로젝트 실행·입력·빌드 경로 확인 | 개발 중심 | 현재 프로젝트를 열어 실행하고 시험 빌드를 만들 수 있는 증거 | 기존 기획 결정과 독립적으로 시작 가능 |
| 첫 구간 구현·통합·함께 확인 | 개발 통합, 관련 파트 검토 | 약속한 플레이 결과 재현 + 발견한 문제 기록 | 해당 구간의 진행표·콘텐츠·공간. 정식 아트 필수 여부는 범위에서 결정 |

이슈 본문은 `목적 / 산출물 / 완료 기준 / 선행 작업 / 근거` 정도로 충분하다. 결정 작업의 완료 기준에는 **결정문과 영향받는 기획의 반영**을 포함한다. 구현 작업에는 **재현 가능한 동작 증거**를 포함한다.

문서의 `제안·합의`와 이슈의 `진행 상태`는 다른 정보다. 기획 문서를 쓰는 작업이 끝나도, 게임에 통합하는 작업은 별도로 남을 수 있다.

사이클을 사용한다면 담당자가 실제 투입할 수 있고 선행 입력을 확보한 작업만 넣는다. 사이클 없이 운영한다면 같은 기준으로 주간 약속을 정한다. 기간이 끝날 때는 `완료한 결과 / 남은 이유 / 다음 조치`로 재판단하고, 남은 작업을 자동으로 같은 약속으로 이월하지 않는다.

## 8. 위키만으로 확정할 수 없는 운영 정보

- 현재 각자의 역할·주당 투입 가능 시간과, PM·최종 결정 책임.
- 실제 개발 저장소의 실행 상태 및 재사용할 코드·씬·아트.
- 미반영 외부 기획 중 이미 작성된 결과와 현재 검토 상태.
- 다음 외부 마감, 데모 범위, 목표 일정의 유효성.

이 항목은 현황표·착수 후보를 만드는 데 방해되지 않는다. **실제 담당·마감과 첫 사이클 작업량을 확정할 때 필요한 입력**이다.
