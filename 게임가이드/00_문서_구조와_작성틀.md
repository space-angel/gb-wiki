# 문서 구조와 작성 틀

팀원에게 공유하는 게임 문서를 **use-funnel 문서 사이트 방식**으로 재구성하기 위한 설계. 구조와 페이지 틀만 먼저 잡는다.

---

## 1. 왜 다시 짜는가

지금 `게임문서/`는 **찾기 좋게** 만들어져 있다. "메인 유품 뭐야?"를 물으면 파일 하나가 답한다. LLM에 물리기엔 이게 맞다.

그런데 **처음 보는 사람에게는 쓸 수 없다.** 27개 파일이 나란히 있고, 어디서 시작해 어디까지 읽어야 하는지 알려주는 게 없다. 그리고 더 중요한 문제:

> **"왜 그렇게 정했나"가 각 문서 안에 흩어져 있다.**
>
> ADR-2가 가중 합산을 버린 이유는 지금 `01-02` 본문 중간에 "설계 의도" 상자로 들어가 있다. 그런데 팀에서 가장 자주 다시 올라오는 논의가 정확히 이런 것들이다. 이유가 문서 중간에 묻혀 있으면 같은 논의를 또 한다.

use-funnel은 이 둘을 분리해서 해결한다. **레퍼런스는 "무엇"만, 심화는 "왜"만** 다룬다. 그리고 앞에 **소개·가이드**를 둬서 진입 경로를 만든다.

---

## 2. use-funnel에서 가져오는 것

실제 문서를 읽고 추린 패턴 5가지.

| 패턴 | use-funnel | 우리 적용 |
|---|---|---|
| **학습 여정** | 소개 → 가이드 → 레퍼런스 → 심화 → 예제 | 그대로 |
| **문제-해결 서술** | "@use-funnel 없이는…" → 불편 나열 → "사용하면…" | "이 규칙이 없으면…" → 무슨 일이 생기나 → "그래서 이렇게 정했다" |
| **용어는 한 번에 3개** | step / context / history 딱 셋 | 이해도 / 유품 / 사령세계 셋 |
| **추상 정의 대신 구체 예시** | 회원가입 플로우 실물 | 김태현 케이스 실물 |
| **페이지마다 다음 링크** | 끝에 "다음은 →" | 그대로 |

**톤**: 대화체(`~해요`)를 쓴다. 지금 문서는 `~다`체로 쓰여 있는데, 팀원용 공유 문서에는 대화체가 더 맞다. 단 **레퍼런스 섹션의 "절대 규칙"만 `~한다`체를 유지**한다 — 규칙은 단정적으로 읽혀야 한다.

**가져오지 않는 것**: use-funnel의 "설치/마이그레이션"은 라이브러리 고유라 대응이 없다. 대신 그 자리에 **"내 파트 찾기"** 를 넣는다.

## 3. 구조

```
📘 1. 소개              처음 온 사람이 5분에 파악
   ├─ 개요                이 게임이 뭔가 · 코어 루프 · 핵심 용어 3개
   └─ 핵심 원칙           문제-해결로 설명하는 설계 원칙 3가지

📗 2. 가이드            내가 뭘 해야 하나
   ├─ 시작하기            30분 온보딩 순서
   ├─ 내 파트 찾기        스토리 / 시스템 / 아트 / 개발별 읽을 것 + 지킬 것
   └─ 문서 규칙           상태 배지 · 어디에 뭘 쓰나 · 갈림 발견 시

📙 3. 레퍼런스          "무엇이 참인가"만
   ├─ 이해도              정의 · 플래그 · 출력 · 판정
   ├─ 유품과 추리         아이템 위계 · 재구성 보드 · 가설과 오답 · 종결 분기
   ├─ 세계와 공간         사령세계 구조 · 공간 개방 · 시점
   ├─ 전투
   └─ 구현                3계층 분리

📕 4. 심화              "왜 그렇게 정했나"만  ← 신규
   ├─ 왜 4플래그인가       가중 합산을 버린 이유
   ├─ 왜 회피만인가        패링·가드를 뺀 이유
   ├─ 왜 판매 여부가 위계인가
   ├─ 왜 보스방을 분리했나
   └─ 왜 이해도를 안 보여주나

📓 5. 예제              실제로 이렇게 적용된다  ← 챕터1이 여기로
   ├─ 챕터1 한눈에
   ├─ 사건과 인물
   ├─ 유품과 조사축
   └─ 플레이어 경험 설계

📔 6. 현황              지금 상태
   ├─ 결정 이력 (ADR)
   ├─ 미결 항목
   └─ 검토 필요
```

### 기존 `게임문서/`와의 관계

**새로 쓰는 건 1·2·4번뿐이다.** 3·5·6번은 기존 27개 파일을 **재배치**한다.

| 신규 | 기존 |
|---|---|
| 1. 소개 | 신규 작성 (`00_요약` 일부 활용) |
| 2. 가이드 | **신규 작성** |
| 3. 레퍼런스 | `01_시스템` · `02_세계` · `03_전투` · `05_구현` 이동 |
| 4. 심화 | **신규 작성** — 각 레퍼런스 문서의 "설계 의도"·"기각된 대안"을 뽑아 모음 |
| 5. 예제 | `04_챕터1` 8개를 4개로 병합 |
| 6. 현황 | `06_상태` 3개 이동 |

**중요**: 심화로 "왜"를 뽑아내면 레퍼런스 문서에서는 그 부분을 **지우고 링크만 남긴다.** 양쪽에 두면 드리프트한다. 한 사실은 한 곳에만.

LLM용 `LLM.md` 라우팅 표는 유지한다 — 파일 ID(`01-05`)를 그대로 쓰므로 재배치해도 인용이 안 깨진다.

## 4. 페이지 작성 틀 5종

페이지마다 유형을 정하고 그 틀을 따른다. 섞지 않는다.

### 틀 A — 개요형 (소개)

```markdown
# 개요

한 문장으로 이 게임이 뭔지. (2~3줄, 대화체)

[코어 루프 다이어그램 또는 스크린샷]

## 개념

이 문서 전체에서 쓰는 말 **딱 3개**만 정의해요.

- **이해도** — …
- **유품** — …
- **사령세계** — …

각 용어를 위 그림의 어디에 해당하는지로 설명해요. 추상 정의를 쓰지 않아요.

---
다음은 [핵심 원칙](…)을 보세요.
```

> use-funnel 개요가 step/context/history 셋만 정의하고 회원가입 플로우 그림으로 설명하는 방식.

### 틀 B — 원칙형 (문제-해결)

```markdown
# 이해도는 전투력이 아니에요

## 이 규칙이 없으면

(무슨 일이 생기는지 구체적으로. 나쁜 예를 실제로 보여줌)

- 문제 1
- 문제 2

## 그래서 이렇게 정했어요

(결정 내용)

## 얻는 것

- 이점 1
- 이점 2

## 대신 감당하는 것

(트레이드오프를 숨기지 않음)

---
근거: ADR-1 · 규칙 전문: [01-01](…)
```

> use-funnel `features` 페이지의 "없이는 / 사용하면" 대비 구조. **나쁜 예를 먼저 보여주는 게 핵심**이다.

### 틀 C — 규칙형 (레퍼런스)

```markdown
---
문서ID: 01-05
상태: 확정
근거: ADR-3
갱신일: 2026-08-05
---

> **한 줄**: (조각 검색만 걸려도 정답이 나오는 한 문장)

# 아이템 위계

## 규칙

(표 위주. 서술 최소화)

## 절대 규칙

1. …한다        ← 이 섹션만 `~한다`체
2. …하지 않는다

## 하면 안 되는 것

| 사례 | 왜 안 되나 |
|---|---|

## 미정

| 항목 | 결정 트리거 |
|---|---|

---
왜 이렇게 정했나 → [왜 판매 여부가 위계인가](…)
관련 → `01-02` · `01-06`
```

> 지금 `게임문서` 형식을 거의 유지. 차이는 **"설계 의도"를 본문에서 빼고 심화로 링크**하는 것.

### 틀 D — 심화형 (왜)

```markdown
# 왜 4플래그인가

## 무엇이 문제였나

(결정 당시 상황. 무엇이 막혀 있었나)

## 검토한 대안

| 대안 | 장점 | 기각 사유 |
|---|---|---|

## 채택한 이유 — 한 가지가 결정적이었어요

(가장 중요한 논거 하나를 강조. 나머지는 부수 효과로)

## 다시 논의될 때 확인할 것

(이 논의가 재발할 때 먼저 읽어야 할 문장)

---
규칙 전문 → `01-02` · 원문 → ADR-2
```

> **신규 유형.** use-funnel의 "심화" 섹션 역할. "다시 논의될 때 확인할 것"은 우리 팀 문제(같은 논의 반복)에 맞춘 추가 항목.

### 틀 E — 사례형 (예제)

```markdown
# 유품과 조사축

챕터1에서 규칙이 실제로 어떻게 적용됐는지 봐요.

## 적용 결과

(표. 규칙 → 실제 값)

## 규칙과 다른 부분

| 항목 | 규칙 | 챕터1 | 왜 |
|---|---|---|---|

## 아직 안 정해진 것

---
규칙 → `01-05` · 전체 흐름 → [챕터1 한눈에](…)
```

---

## 5. 공통 규칙

- **모든 페이지는 `> 한 줄`로 시작한다.** 조각만 읽혀도 정답이 나와야 한다 (LLM 검색 대응)
- **페이지 끝에 "다음은 →"** 을 둔다. 학습 순서가 끊기지 않게
- **상태 배지**를 제목 옆에 붙인다 — `확정` / `잠정` / `미정` / `검토필요`
- **`검토필요`는 한쪽을 골라 쓰지 않는다.** 양쪽을 보여주고 `06-03`으로 보낸다
- **한 사실은 한 페이지에만.** 다른 곳에선 링크
- 대화체(`~해요`). **단 "절대 규칙" 섹션만 `~한다`체**

## 6. 지금 만든 샘플

판단용으로 양 끝 유형 2개를 실제로 썼다.

| 파일 | 틀 | 왜 이걸 골랐나 |
|---|---|---|
| `1_소개/개요.md` | A | 진입점. 톤과 용어 정의 방식을 볼 수 있음 |
| `4_심화/왜-4플래그인가.md` | D | 신규 유형. 이 섹션이 실제로 유용한지가 이 설계의 핵심 |

## 7. 남은 결정

- 6개 섹션 이름 확정 (소개/가이드/레퍼런스/심화/예제/현황)
- 심화 페이지를 몇 개로 할지 (지금 5개 후보)
- 예제 섹션에서 챕터1 8개 → 4개 병합 시 무엇을 합칠지
- 대화체 전환을 전체에 적용할지, 신규 섹션(1·2·4)만 할지
