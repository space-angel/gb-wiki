# 이슈 컨벤션 — 익숙한 제목과 친절한 설명

**2026-09-08 합의·적용:** 본문은 `왜 필요한지 / 할 일 / 완료 기준 / 참고·인계` 네 항목을 사용합니다. 어려운 용어를 풀어서 설명합니다. 제목은 사용자가 선호한 파트·작업 중심의 **`[파트] 구체적인 작업`**을 사용합니다. 이 형식으로 GBG-247~253을 등록했습니다.

## 제목을 이렇게 쓰면 어떨까요

**`[기획·스토리·아트·개발 중 하나] 대상 + 구체적인 작업`**

| 파트 | 제목 예시 |
|---|---|
| 기획 | [기획] 첫 조사 구간의 행동과 반응 정리 |
| 스토리 | [스토리] 이유미의 조사 전·후 대사 작성 |
| 아트 | [아트] 첫 조사 공간과 대화창 배치 그리기 |
| 개발 | [개발] 조사 여부에 따른 이유미 대사 연결 |

사운드처럼 독립 작업이 생기면 해당 파트를 추가할 수 있습니다. 당장은 실제 첫 작업에 필요한 네 파트로 시작합니다. 역할이 겹치는 작업도 담당자 한 사람과 주된 파트 하나를 정하고, 함께 확인할 사람은 본문에 적습니다.

### 처음 결과 중심을 추천한 이유

`대화 시스템 구현`은 끝나는 범위가 넓습니다. 대화창·조건·선택지·저장 중 어디까지인지 제목으로는 알기 어렵습니다. `조사 후 NPC 반응이 바뀐다`는 확인할 동작을 드러내므로 기획·스토리·아트·개발이 같은 결과를 보며 이야기하기 쉽습니다.

팀이 파트 중심 제목에 익숙하므로 **파트를 먼저 보여주고, 구체적인 대상을 붙이는 방식**이 잘 맞겠습니다. 결과 중심의 장점은 첫 설명과 완료 기준에서 살립니다. 제목을 모두 플레이 문장으로 바꿀 필요는 없습니다.

예: `[개발] NPC 시스템 구현` → **`[개발] 조사 여부에 따른 이유미 대사 연결`**. 첫 설명은 “물건을 본 뒤 이유미의 말을 다시 들어보는 경험을 확인하려고 해요.”로 시작합니다.

## 본문은 네 항목

```markdown
## 왜 필요한지
이번 작업이 게임이나 다음 사람의 작업에 어떤 도움이 되는지 1~2문장으로 적어요.

## 할 일
- 이번에 작업할 대상과 범위를 적어요.
- 무엇부터 하면 되는지 알려주세요. 이번에 하지 않아도 되는 일은 필요할 때만 한 줄 적어요.

## 완료 기준
- [ ] 작업한 사람이 스스로 확인할 수 있는 결과를 적어요.
- [ ] 받는 사람이 무엇을 보고 확인하면 되는지 적어요.

## 참고·인계
- 참고: 바로 필요한 문서나 그림과 읽을 부분.
- 먼저 필요한 것: 다른 작업이 필요하면 링크와 필요한 결과.
- 전달: 결과물을 어디에 두고 누구에게 알려주면 되는지.
- 막히면: 누구와 어떤 내용을 상의하면 되는지.
```

목적·실행·완료 기준을 같은 문장으로 반복하지 않습니다. 네 항목을 채우기 위해 의미 없는 문장을 늘리지 않습니다. 작은 작업은 전체 10줄 안팎이어도 충분하고, 조건이 있는 작업만 더 자세히 적습니다.

## 친구들이 바로 시작할 수 있게 쓰는 기준

| 어려워질 수 있는 표현 | 실제로 할 행동으로 바꾸기 |
|---|---|
| 상태 플래그 연동 | 물건을 조사했는지 기억해서, 그에 맞는 대사가 나오게 해주세요 |
| 콘텐츠 스키마 정의 | 물건 이름·말하는 사람·대사가 나오는 조건을 같은 표에 적어주세요 |
| 그레이박스 제작 | 임시 도형으로 걸을 곳과 막힌 곳을 만들어주세요 |
| 에셋 파이프라인 검증 | 그림 파일을 게임에 넣고 크기와 표시가 맞는지 확인해주세요 |
| 수용 기준 충족 | 아래 순서로 직접 해보고 같은 결과가 나오는지 확인해주세요 |
| 디펜던시 해소 | 먼저 필요한 대사나 그림이 준비됐는지 확인해주세요 |

개발 담당에게 필요한 정확한 기술 용어는 사용할 수 있습니다. 다른 파트가 읽어야 하는 요구 사항은 일상적인 행동으로 설명하고, 자세한 개발 메모는 참고 링크나 별도 메모로 둡니다.

모르는 설계를 당연한 전제로 적지 않습니다. 정해야 할 것이 있으면 “조사 전·후에 어느 정보까지 말할지는 지호와 함께 정해주세요”처럼 **질문과 상의할 사람**을 알려줍니다.

## 한 이슈의 크기와 완료

- **담당자 한 사람, 중심 결과물 하나.** 짧은 확인·수정은 체크리스트로 묶습니다.
- 다른 담당자에게 넘어가거나, 먼저 끝나야 다음 작업을 시작할 수 있으면 이슈를 나눕니다.
- 기본 이동·카메라·충돌을 무조건 세 장으로 나누지는 않습니다. 작은 이동 시험으로 함께 확인할 수 있으면 하나로 묶습니다.
- 기획·대사·그림은 다음 사람이 쓸 수 있는 결과와 확인이 있어야 완료입니다. 최종 게임에 적용된 것과는 구분합니다.
- 개발은 약속한 동작을 직접 확인할 수 있어야 완료입니다. 코드 작성·병합만으로 게임 동작 확인을 대신하지 않습니다.
- 조사 작업은 확인 결과와 다음 조치가 있으면 완료할 수 있습니다. 발견한 오류가 해결됐다는 뜻으로 사용하지 않습니다.

## Linear 필드에 넣을 정보

| 정보 | 위치·제안 |
|---|---|
| 파트 | 제목 앞 `[파트]`. 파트 라벨은 필터가 필요할 때 같은 값으로 사용 |
| 담당자 | Assignee 한 사람 |
| 상태 | 백로그 / 할 일 / 작업중 / 검토 / 완료 / 취소됨 |
| 이번 기간의 약속 | Cycle. 담당자 가용량 확인 후 지정 |
| 어느 결과에 기여하는지 | Project와 Milestone |
| 우선순위 | 기본 Normal. 다음 일을 막는 착수 준비만 High. Urgent는 즉시 대응이 필요한 실제 문제 |
| 날짜 | 실제 합의한 전달·외부 마감이 있을 때만 Due date |
| 작업량 | 첫 회의에서는 본인 가용 시간·예상 소요로 확인. 포인트 체계는 일단 추가하지 않음 |
| 먼저 끝나야 할 작업 | blocked-by 관계와 본문의 필요한 결과 |

회의 안건·규칙 안내를 별도의 업무 이슈로 계속 만들지 않습니다. 안내는 문서에, 실제 해야 하는 결정·제작·수정은 이슈에 둡니다.
