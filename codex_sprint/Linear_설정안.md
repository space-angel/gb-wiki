# Linear 새 설정안

**이슈 등록은 완료했고 팀 설정은 적용 전입니다.** 사용자의 요청에 따라 기존 이슈 복원·이관 없이 신규 이슈로 구성했습니다. 프로젝트·마일스톤·사이클·상태·라벨 설정은 아래 안을 유지합니다.

| 보관 포함 이슈 목록 | 103건, 추가 페이지 없음 | 삭제된 항목도 포함됨. 103건 전부를 보관 상태로 단정하지 않음 |

개별 확인한 [GBG-236](https://linear.app/wozz/issue/GBG-236)은 상태명이 `작업중`이어도 9/8 활동에 `trashed=true`가 있습니다. 따라서 과거 상태명을 지금 수행 중인 일로 집계하지 않았습니다. 과거 제목·담당·마감을 새 작업으로 가져오지 않습니다.

상세 조회 범위와 상태·라벨 목록은 [조회 스냅샷](부록/Linear_조회스냅샷.json)에 있습니다. 실제 반영 직전에는 현재 설정을 다시 읽습니다.

## 목표 구조

```text
공방게이밍 · GBG
└─ 신규 Project: ATK_DEF — 챕터1 데모
   ├─ M0 출발점과 첫 실험 정의
   ├─ M1 첫 조사 플레이
   ├─ M2 짧은 추리·재해석 플레이
   ├─ M3 세계·전투·처분 연결
   ├─ M4 챕터1 범위 통합
   └─ M5 데모 마감과 전달

Cycle: 2주 동안 실제로 약속한 작업
Issue: 한 사람이 맡는 구체적인 작업
```

프로젝트는 함께 만들 결과, 마일스톤은 그 안의 단계, 사이클은 일하는 기간입니다. 프로젝트 안에 마일스톤을 두고 이슈를 연결할 수 있으며, 마일스톤 날짜는 선택 사항입니다. [Linear 마일스톤 안내](https://linear.app/docs/project-milestones)

프로젝트 설명 초안:

> 작은 조사 구간의 직접 실행부터 시작해, 추리·재해석과 세계·전투·처분의 연결을 확인합니다. 검증 결과에 따라 챕터1 데모 범위를 정합니다. 현재 플레이 가능한 빌드는 없고, ADR 외 기획은 작업 중입니다. 단계 통과는 실행 결과와 공동 플레이로 판단합니다.

프로젝트 리드는 오늘 정한 조율 담당, 초기 상태는 팀 합의에 맞는 계획 상태로 둡니다. 실제 착수 때 진행 상태로 바꿉니다. 데모 마감일과 먼 단계 날짜는 비워 둡니다. 실제 목표는 [새 로드맵](로드맵.md)의 단계별 기준을 연결합니다.

## 상태는 자주 쓰는 여섯 개로

| 상태 | Linear 종류 | 이렇게 사용할 제안 |
|---|---|---|
| 백로그 | backlog | 후보. 이번 기간의 약속이 아직 아님. 신규 기본 상태 |
| 할 일 | unstarted | 담당·범위·완료 기준을 합의. 약속한 선행 작업을 기다릴 수 있음 |
| 작업중 | started | 지금 직접 작업하는 한 건. 시작에 필요한 입력 확보 |
| 검토 | started | 결과물을 공유하고, 본문에 적은 사람이 확인하는 중 |
| 완료 | completed | 해당 이슈의 완료 기준과 확인이 충족됨 |
| 취소됨 | canceled | 더 하지 않기로 결정한 작업. 이유를 남김 |

시스템의 `Duplicate`는 별도로 유지합니다. 기존 검토 세 상태는 `검토` 하나로 통일하는 설정을 제안합니다. 적용할 때 사용 중인 항목을 확인하고, 새 이슈에서 사용할 상태를 한 가지로 맞춥니다. 상태 설정은 팀별이며 Duplicate는 시스템이 관리합니다. [Linear 상태 안내](https://linear.app/docs/configuring-workflows)

`막힘`은 별도 상태 대신 **막힘 라벨 + 필요한 것·확인 담당·다음 확인 시점**으로 표시합니다. 다른 이슈가 원인이면 `blocked by` 관계도 연결합니다. 다음 일을 진행할 수 없을 때 표시하는 관계이며, 원인 이슈가 해결되면 관련 이슈 관계로 전환됩니다. [Linear 관계 안내](https://linear.app/docs/issue-relations)

이미 시작한 작업이 막히면 작업중에 막힘을 표시합니다. 대기 중 다른 작업을 시작할 때는 기존 건을 `할 일`로 돌려 두고 이유를 남겨, 개인 작업중 1건 원칙을 유지합니다. 더 이상 이번 사이클에 약속하지 않는다면 사이클에서도 빼고 백로그로 돌립니다.

## 라벨과 화면

새 이슈의 파트 라벨은 제목과 같은 **기획 / 스토리 / 아트 / 개발** 중 하나를 사용하도록 제안합니다. 추가 표시는 `막힘`만 먼저 둡니다. 같은 이름의 아트·개발 라벨은 기존 설정을 사용할 수 있지만, 기존 이슈의 라벨·내용을 옮기지는 않습니다. 기획·스토리·막힘은 현재 이름 목록에 없으므로 새 설정 후보입니다.

이전 라벨은 신규 작업에 붙이지 않습니다. 과거 기록을 바꾸기 위한 일괄 삭제·이름 변경은 이번 설정의 필수 작업으로 잡지 않습니다. 우선순위·마일스톤·완료 여부를 라벨로 중복 관리하지 않습니다.

| 화면 이름 | 필터·표시 제안 | 볼 때 |
|---|---|---|
| 이번 사이클 | GBG + 신규 프로젝트 + 현재 Cycle, 상태별 보드 | 팀이 약속한 전체 작업 |
| 내 할 일 | 신규 프로젝트 + 내 담당 + 미완료, 우선순위 정렬 | 각자 작업 시작 |
| 검토할 것 | 신규 프로젝트 + 검토 상태, 담당·결과 링크 확인 | 다음 사람에게 넘길 결과 |
| 막힌 것 | 신규 프로젝트 + 막힘 라벨 + 미완료 | 도움이 필요한 곳 |

내 할 일은 개인 화면을 사용하고, 팀이 같이 볼 나머지 목록은 공유 뷰로 저장합니다. 필터한 목록·보드를 저장하고 공유할 수 있습니다. [Linear 뷰 안내](https://linear.app/docs/custom-views)

## 사이클 설정 제안

| 항목 | 제안값 |
|---|---|
| 기간 | 2주 |
| 시작 요일 / 시간대 | 수요일 / Asia/Seoul |
| 첫 일정 | 2026-09-09~09-22 작업 기간 제안. 실제 화면의 시작·종료 경계 확인 |
| 다음 사이클 | 가까운 다음 1개만 운영에 사용. 먼 미래 작업은 로드맵에 둠 |
| 별도 휴지 기간 | 없음. 검토·수정 시간은 사이클 가용량 안에 확보 |
| 진행·완료 이슈 자동 추가 | 초기에는 끔. 약속한 작업을 직접 선택 |
| 자동 종료 | 오래됐다는 이유로 업무를 닫는 자동화는 초기에는 끔 |
| 작업량 포인트 | 초기에는 사용하지 않음. 본인의 가용 시간으로 범위를 합의 |

사이클은 반복되는 일정이고 팀 시간대에 맞춰 시작합니다. 미완료 작업의 **자동 이월은 진행·완료 이슈 자동 추가와 별개**이므로, 자동 추가를 껐다고 이월이 멈추지는 않습니다. [Linear 사이클 안내](https://linear.app/docs/use-cycles)

따라서 종료 전에 남은 작업을 다음처럼 처리합니다.

1. 다음에도 하기로 약속한 작업: 남은 범위와 작업량을 갱신하고 다음 사이클 배정을 확인합니다.
2. 다음 약속에서 제외한 작업: 종료 전에 사이클을 제거하고 백로그로 돌립니다.
3. 필요 없어진 작업: 이유를 남기고 취소합니다. 중복은 원본을 정해 Duplicate 처리합니다.
4. 자동 이월된 작업: 다음 사이클 시작 때 원래 약속인지 다시 확인하고, 아니라면 사이클 밖으로 옮깁니다.

실제 사이클 설정을 아직 확인하지 않았으므로 기존 사이클을 즉시 종료하거나 시작일을 앞당기는 조작은 전제하지 않습니다.
