# Notion 위치 지도

`gb_wiki/wiki/협업환경_설계/Notion_페이지_구조_설계.md`(목표 구조를 정의했던 원 설계 문서)가
2026-08-17 레거시 정리 중 실수로 삭제되어 복구 불가능하다. 이 문서는 그 자리를 대신해서
**"지금 Notion에 뭐가 실제로 있고, 자동 대조 파이프라인이 어디를 봐야 하는지"**를 다시 잡아둔
것이다 — 예전 설계처럼 새 구조를 만들려는 문서가 아니라, **있는 그대로를 지도화**한 것.

## 원칙 — 무엇을 다시 안 하는가

`프로젝트_위키/00_위키_설계.md`(2026-08-05)가 이미 실측으로 확인한 실패 원인을 반복하지 않는다:
DB 속성·relation·rollup을 사람이 계속 채워야 하는 구조는 4인 팀이 유지 못 한다("확정 레퍼런스
DB"는 설계만 되고 끝내 안 만들어짐). 그래서 이 지도는 **사람에게 새로운 입력 의무를 만들지
않는다** — 다들 지금처럼 각자 샌드박스에 어수선하게 쓰면 되고, 감지는 전부 `최종 편집 일시` 하나로
한다.

## 1. 변경 감지 소스 — `ATK_DEF 라이브러리` (Notion Wiki DB)

- Database ID: `32e8826f-8563-805c-a763-cce456b9c486`
- Data source: `collection://3418826f-8563-80ad-83bc-000b9ec72cb5`
- Wiki page: `https://app.notion.com/p/3418826f856380298e78c79ffe009b65`

2026-08-13경 Notion의 "워크스페이스를 위키로 전환" 기능으로 자동 생성된 것으로 보인다. `상위
페이지`/`하위 페이지` relation은 대부분 비어 있어 **계층 구조로는 못 쓴다.** 하지만 워크스페이스
전체 페이지를 `최종 편집 일시` 컬럼과 함께 SQL 한 방으로 긁을 수 있다는 점에서 **변경 감지용으로는
그대로 쓸 수 있다.** 새 DB를 만들 필요 없음.

```sql
SELECT url, "페이지", "소유자", "최종 편집 일시"
FROM "collection://3418826f-8563-80ad-83bc-000b9ec72cb5"
WHERE "최종 편집 일시" > '<마지막_동기화_시점>'
ORDER BY "최종 편집 일시" DESC
```

`<마지막_동기화_시점>`은 [[../03_진단문서/마지막_동기화]]에 기록된 값을 쓴다. `/wiki-sync`
Stage 0은 이제 샌드박스를 하나씩 도는 대신 이 쿼리 하나로 시작한다.

## 4. `게임문서` — 확정 콘텐츠 사람용 미러 (2026-08-17 신설, **수동 유지**)

- 위치: `ATK_DEF 위키` 허브 하위 `📚 게임문서` 페이지 (`3bf8826f856380daac43f2850104eaee`)
- 내용: `게임가이드/`의 2026-08-17 시점 스냅샷을 사람이 직접 붙여넣은 것. 페이지 이름은 옛
  `게임문서/`(현재 삭제됨) 폴더의 flat ID 체계(`00_요약`, `01-01_...` 등)를 그대로 씀 — 게임가이드의
  `3_레퍼런스`/`4_심화`/`5_예제` 폴더 구조와는 이름 매핑이 다르니 대응시킬 때 주의.
- **wiki-sync는 이 페이지를 절대 안 건드린다.** 자동 갱신 대상이 아니라 사람이 필요할 때만 다시
  붙여넣는 스냅샷이다 — 2026-08-17 사용자 결정.
- 승격 기준(합의됨): **ADR이 Accepted로 잠기거나 `06-03`의 갈림이 해소될 때만** 해당 페이지를
  사람이 다시 붙여넣는다. 그 외 매주 자동 실행 결과(위반 수정 등)는 여기 반영 안 됨 — 팀원이 최신
  확정 사실을 원하면 결국 `게임가이드/`(GitHub) 또는 이 지도의 Notion 로그 페이지를 봐야 한다.
- 2단 구조: **sandbox(자유, 초안)** → (ADR 확정/갈림 해소 시에만) → **게임문서(사람이 수동 갱신,
  확정 콘텐츠 열람용)**. sandbox 쪽 규칙은 안 만든다 — 어수선한 게 정상이라는 원칙 유지.

## 5. Slack·Linear 구조 + 협업 프로세스 가이드 (2026-08-17 신설)

팀이 Slack·Notion·Linear를 다 갖춰놓고도 아무도 뭘 언제 써야 하는지 몰라서 안 쓰던 문제를 짚고,
"초안(sandbox) → ADR(Notion) → 토론(Slack `#0_결정논의_큐`) → 검토(Linear `D`트랙) → 확정" 흐름을
가이드로 정리해 Notion `📅 회의록·프로세스` 스텁을 채웠다(§3의 표에서 이제 제외).

### Linear — 실제 워크스페이스 구조 (2026-08-17, `orca linear` CLI로 확인)

MCP에 연결된 Linear 계정은 팀 계정과 다른 개인 계정(`Personal`)이라 팀 데이터가 안 보였다. 대신
`orca linear` CLI(`~/.orca/linear-workspaces.json`에 별도 인증 저장됨)로 실제 팀 워크스페이스에
접근함 — Notion 워크스페이스명과 동일한 `Wozz`(urlKey: `wozz`) 계정이었다.

- Workspace ID: `08e92c02-0ad7-4873-ac87-fc7b0da44a41`
- 팀: `GBG` (공방게이밍 Workspace) / 프로젝트: `챕터1 데모 제작`
- 상태값: `백로그 → 할 일 → 작업중 → 완료` / `취소됨` · `Duplicate` · `In Review` · `검토 대기` ·
  `검토중` (뒤 세 개가 전부 `started` 타입으로 겹치는데, 사용자가 "필요해서 둔 것"이라 확인 —
  정리하지 않음)
- 이슈 네이밍 컨벤션(6월부터 이미 쓰던 패턴, 새로 안 만듦): `E{에픽}-{트랙}[-T{번호}]. 설명`
  — `S`=시스템, `D`=설계결정(ADR 검토용), `A/B/C...`=플레이 기능 순서, `-T`=구현 세부작업.
  상위 항목은 마침표(`.`), T 하위 작업은 콜론(`:`)으로 표기 — 32개 이슈 전수 확인, 예외 없음
- 확인 당시 이슈 32개 중 19개(약 60%)가 담당자 미배정 상태 — 프로세스 가이드에서 이 수치를
  "Linear 상태를 옮겨야 하는 이유" 근거로 그대로 인용함
